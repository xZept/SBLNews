# Idea Research: User Profiles & Account Menu

- **Slug**: user-profiles
- **Created**: 2026-11-26T23:16:00+08:00
- **Evidence confidence (overall)**: high

## Users & Demand

- **Direct product owner request for profile customization and top-right account bubble**: The user wants signed-in users to press a top-right avatar icon (initially showing their name initials when no profile photo is set) to open a popover bubble containing Profile, Theme (light/dark), and Sign out, and wants guidance on what other profile fields users should be able to modify and what else belongs in the bubble. — [source: .specify/assessments/user-profiles/intake.md] (confidence: high, cited)
- **Current signed-in UX lacks profile control**: In `TopNav`, signed-in users currently see a static text string pulled from OAuth `auth.users` metadata (`user.user_metadata?.full_name || user.user_metadata?.user_name || user.email || "Signed in"`) beside a standalone "Sign out" button. Users cannot modify how their name appears on `/study/[id]` comments, cannot set or remove a profile photo, and have no theme switch. — [source: web/src/components/layout/top-nav.tsx#L145-L173, web/src/components/study/discussion-thread.tsx#L214] (confidence: high, cited)
- **Domain context in study discussions**: Target users are lifters, strength coaches, and exercise-science readers discussing peer-reviewed methodology on `/study/[id]`. Allowing optional domain metadata on a profile (such as a role/background tag like *Lifter*, *Strength Coach*, *Exercise Researcher*, *Clinician* or a short credentials/training bio) adds useful credibility context to comments without requiring a full social network. — [source: specs/001-sbl-news-mvp/spec.md#L10-L12, ASSUMPTION] (confidence: medium, assumption)
- **No quantitative post-launch usage telemetry yet**: Because the `001-sbl-news-mvp` codebase was just implemented, there are no production support tickets or user analytics logs in the repository. — [source: specs/001-sbl-news-mvp/spec.md] (confidence: high, cited)

## Prior Art

- **Existing `public.profiles` schema and self-update RLS policy**: `supabase/migrations/0002_tables_and_indexes.sql` already defines `public.profiles` (`id`, `display_name`, `avatar_url`, `role`, `created_at`). `supabase/migrations/0003_rls_policies_and_triggers.sql` already enables `profiles_select_public` (`USING (true)`), `profiles_update_own` (`USING (auth.uid() = id) WITH CHECK (auth.uid() = id)`), and the `trg_protect_profile_role` trigger preventing non-admins from escalating their `role` column during self-updates. — [source: supabase/migrations/0002_tables_and_indexes.sql#L5-L12, supabase/migrations/0003_rls_policies_and_triggers.sql#L30-L61] (confidence: high, cited)
- **OAuth `handle_new_user()` trigger behavior vs. initials default**: `0003_rls_policies_and_triggers.sql` automatically copies `raw_user_meta_data->>'avatar_url'` from Google/GitHub into `public.profiles.avatar_url` when a user is created. Because Google and GitHub almost always supply a default `avatar_url`, `profiles.avatar_url` will already be non-null on first login unless the trigger leaves `avatar_url` null on signup (or tracks whether a custom avatar was set) so that the requested "initially set to their name initials when no profile is set yet" behavior actually occurs. — [source: supabase/migrations/0003_rls_policies_and_triggers.sql#L179-L212] (confidence: high, cited)
- **`TopNav` reads `auth.users` metadata instead of `public.profiles`**: `TopNav` currently fetches only `profiles.role` (via `fetchIsAdmin`) and displays `user.user_metadata?.full_name` from the Supabase Auth session object. Any updates to `public.profiles` (`display_name`, `avatar_url`, `theme_preference`, etc.) require `TopNav` to query `public.profiles` for the signed-in user's row. — [source: web/src/components/layout/top-nav.tsx#L20-L35, L157-L162] (confidence: high, cited)
- **Comments already join `public.profiles` (`display_name`, `avatar_url`)**: `getStudyComments` in `web/src/lib/queries/studies.ts` already selects `author:profiles!comments_author_id_fkey (id, display_name, avatar_url)`, though `CommentItem` in `discussion-thread.tsx` currently renders only `author.display_name` as plain text and ignores `avatar_url`. — [source: web/src/lib/queries/studies.ts#L119-L123, web/src/components/study/discussion-thread.tsx#L214, L281-L286] (confidence: high, cited)
- **Industry pattern for research/community account bubbles (Hugging Face / GitHub / Linear)**: Top-right avatar button opens a compact popover showing: (1) Identity header (Avatar/Initials, Display Name, Email, and Role badge such as `Member` or `Admin`), (2) `Edit Profile` trigger (opening a modal dialog or slide-over sheet), (3) inline `Theme` toggle (`Light` / `Dark` / `System`), (4) conditional `Admin Review Queue` link (`/admin/review`) for admins, and (5) `Sign out` action. — [source: ASSUMPTION] (confidence: high, assumption)

## Market & Context

- **Current user coping mechanism**: Signed-in users must accept whatever display name Google or GitHub OAuth populated at signup, have no avatar or initials badge in the header or comment threads, and are locked into the light canvas (`#F8FAFC`) at all times. — [source: web/src/components/layout/top-nav.tsx, web/src/app/globals.css] (confidence: high, cited)
- **Cost of doing nothing**: Privacy-conscious commenters cannot decouple their SBL News display name from their Google/GitHub account name; mobile header ergonomics remain cramped due to the full "Sign out" button; and users reading studies in low-light environments have no dark-theme option. — [source: web/src/components/layout/top-nav.tsx#L145-L173, ASSUMPTION] (confidence: medium, assumption)

## Data & Constraints

- **Constitution Principle III (Design System & Dark Mode rules)**: Principle III prohibits *"purple, violet, or indigo hues ... color gradients, mesh backgrounds, glassmorphism (`backdrop-blur`), blurry drop-shadows, or dark-mode-by-default themes."* Light mode (`#F8FAFC` canvas, `#FFFFFF` surface, `#0F172A` ink/border, `#38BDF8` Sky Blue accent) MUST remain the default theme. Adding an opt-in Dark Mode requires defining high-contrast Neo-Brutalist dark tokens in `globals.css` (e.g., CSS variables switched via a `data-theme="dark"` or `.dark` root attribute) and replacing hardcoded `#0F172A` shadow literals (such as `shadow-[2px_2px_0px_#0F172A]`) with theme-aware CSS variable shadows (`var(--shadow-control)`, `var(--shadow-card)`). — [source: .specify/memory/constitution.md#L51-L58, web/src/app/globals.css#L9-L32, web/src/components/layout/top-nav.tsx#L132] (confidence: high, cited)
- **Constitution Principle V (6-Route MVP Discipline)**: Principle V confines the app to 6 routes (`/`, `/study/[id]`, `/guidelines`, `/search`, `/methodology`, `/admin/review`). Implementing profile editing via a Neo-Brutalist modal dialog opened from the top-right account bubble satisfies the entire user workflow without adding a 7th route (whereas adding a `/profile` or `/settings` route would require a MINOR constitution amendment). — [source: .specify/memory/constitution.md#L75-L86, L128-L132] (confidence: high, cited)
- **Constitution Principle I & IV ($0/Month Free-Tier & 5 GB Egress Cap)**: Supabase Free provides 1 GB Storage and 5 GB monthly egress. Allowing raw, uncompressed profile photo uploads would risk egress spikes if avatars are rendered across feeds or comment threads. Constraining avatar uploads via client-side canvas downscaling (e.g., `256x256` WebP/JPEG, max `200 KB`) or strict bucket file-size limits (`<= 500 KB`, image MIME types only) inside a dedicated `avatars` storage bucket with per-user RLS (`auth.uid()`) keeps bandwidth negligible. — [source: .specify/memory/constitution.md#L31, L67-L71] (confidence: high, cited)
- **ISR & Theme Flash Prevention**: Because `/` and `/guidelines` are ISR-cached static pages (`revalidate = 3600`), the server cannot pre-render per-user theme classes into the static HTML response without opting out of ISR. Client-side theme initialization via a tiny synchronous `<script>` in `RootLayout` reading `localStorage` (and syncing with `profiles.theme_preference` when authenticated) prevents Flash of Incorrect Theme (FOIT) while keeping `/` and `/guidelines` 100% ISR-cached. — [source: .specify/memory/constitution.md#L30, web/src/app/layout.tsx#L63-L79] (confidence: high, cited)

## Evidence Against the Idea

- **Hardcoded light-mode tokens and shadows across existing components**: Several components use inline shadow arbitrary values (`shadow-[2px_2px_0px_#0F172A]`) and pastel semantic badges (`#A7F3D0`, `#BAE6FD`, etc.) designed for `#0F172A` dark ink on `#FFFFFF` surfaces. Supporting a dark theme requires auditing every component so borders, offset shadows, and semantic badges stay legible and Neo-Brutalist in both light and dark modes. — [source: web/src/components/layout/top-nav.tsx#L132, web/src/app/globals.css#L18-L22] (confidence: high, cited)
- **Storage bucket management overhead**: Adding custom photo uploads introduces a new storage dependency (Supabase Storage `avatars` bucket + storage RLS policies + old-file cleanup or overwrite on `avatars/{user_id}/avatar.webp`), whereas text-only profiles + initials require zero binary storage. — [source: supabase/migrations/0002_tables_and_indexes.sql#L5-L12] (confidence: high, cited)
- **Risk of social-network scope creep**: If profile fields expand into public profile pages, follower graphs, or activity history, the feature will violate Principle V (Scoped Route Discipline) and distract from SBL News's core evidence-discovery mission. — [source: .specify/memory/constitution.md#L75-L86] (confidence: high, cited)

## Gaps & Open Questions

- [NEEDS CLARIFICATION: Which additional editable profile fields should be included alongside photo, display name, and theme preference? (Recommended candidates: `training_background` / role badge e.g. Lifter / Coach / Researcher / Clinician, and a short `bio` / credentials line up to 160 chars; plus read-only email and account role.)]
- [NEEDS CLARIFICATION: Should OAuth login leave `avatar_url` empty by default so new users always start with their name-initials badge until they explicitly upload a photo (or choose to use their OAuth photo)?]
- [NEEDS CLARIFICATION: Should profile editing open as a modal dialog from the top-right account bubble (preserving the 6-route architecture under Constitution Principle V), or as a dedicated `/profile` route (which would require a Constitution Principle V amendment)?]
- [NEEDS CLARIFICATION: Should the theme selector offer strictly `Light` and `Dark` (with `Light` as default per Constitution Principle III), or `Light`, `Dark`, and `System`?]
