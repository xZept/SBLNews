## Opt-In Profile Activity & View Privacy

- [ ] CHK001 Are default visibility requirements (`Private`) explicitly specified for both **Interacted (Upvoted) Studies** and **Recently Viewed Studies** across both newly registered and existing users? [Completeness, Spec §FR-006]
- [ ] CHK002 Are data-access boundary requirements defined so `Private` and `Friends Only` activity rows are excluded at the database/query layer rather than only hidden in UI presentation? [Clarity, Spec §FR-008]
- [ ] CHK003 Does the spec unambiguously define whether switching **Recently Viewed Studies** back to `Private` preserves existing saved rows (hidden from others) versus automatically purging them? [Ambiguity, Spec §Edge Cases]
- [ ] CHK004 Are the scope and boundaries of the **Clear History** control explicitly defined (affecting only **Recently Viewed Studies** without mutating **Upvoted Studies**)? [Clarity, Spec §FR-006]
- [ ] CHK005 Are unauthenticated visitors explicitly excluded from recent-study view tracking, and are the exact opt-in conditions (`Friends Only` or `Public`) for recording views specified? [Completeness, Spec §FR-007]
- [ ] CHK006 Is the 20-study retention cap quantified with deterministic deduplication and tie-breaking rules for repeated views of the same study? [Clarity, Spec §FR-007]

## Friend Connections, Search & Block Semantics

- [ ] CHK007 Are all valid friendship state transitions (`none`, `pending`, `accepted`, `blocked`) and actor permissions (who may accept, decline, cancel, unfriend, or unblock) completely specified? [Completeness, Spec §FR-010]
- [ ] CHK008 Are edge-case requirements defined for self-requests, duplicate/crossed pending requests between two users, and requests targeting a user in a blocked pair? [Coverage, Spec §Edge Cases]
- [ ] CHK009 Are requirements specified for whether declining or cancelling a pending friend request permits immediate re-requesting or imposes a cooldown/rate limit? [Gap, Spec §FR-010]
- [ ] CHK010 Are display-name user search requirements bounded with privacy and anti-enumeration constraints (minimum query length, result limit, excluding users who blocked the searcher, and excluding private profile fields)? [Completeness, Spec §FR-010]
- [ ] CHK011 Are blocking requirements consistent across all affected surfaces: friend requests, 1:1 chat/study sends, and immediate revocation of `Friends Only` profile activity access? [Consistency, Spec §FR-008, §FR-010]
- [ ] CHK012 Does the spec clarify whether a blocked user sees a neutral unavailable state (without revealing who blocked them) and whether prior 1:1 message history becomes hidden or read-only upon blocking? [Ambiguity, Spec §US4-6, §Edge Cases]
- [ ] CHK013 Are unblock permissions unambiguously restricted to the original blocker so the blocked party cannot self-unblock? [Completeness, Data Model §2.5]

## Mutual-Friend Chat & Study-Send Gating

- [ ] CHK014 Are mutual-friend authorization requirements consistently defined across both 1:1 plain-text messages and **Send to Friend** embedded study cards? [Consistency, Spec §FR-004, §FR-011]
- [ ] CHK015 Are input validation boundaries (empty/whitespace rejection, `1,000`-character message cap, `240`-character study-note cap, and plain-text-only / no media attachments) quantified for all messaging inputs? [Clarity, Spec §Edge Cases, §Assumptions]
- [ ] CHK016 Are exception-flow requirements specified for historical 1:1 messages referencing a study that is later unpublished or deleted? [Coverage, Spec §Edge Cases]
- [ ] CHK017 Are unread-count and read-receipt mutation requirements scoped strictly to the message recipient so a sender cannot alter a recipient's read state? [Gap, Spec §US4-5]

## Egress Guardrails, Anti-Gaming & Measurability

- [ ] CHK018 Are strict summary-column projection requirements (`no SELECT *`, excluding `abstract_text`, `embedding`, and private profile fields such as `email`, `role`, and `theme_preference`) specified for friend search, **Top Users**, profile activity lists, and chat study cards? [Completeness, Spec §FR-011, §FR-012]
- [ ] CHK019 Are deterministic **Aura** weights, UTC daily anti-gaming caps, and score-recalculation rules upon deletion/un-endorsement/un-upvote specified without conflict across spec and assumptions? [Consistency, Spec §FR-001, §US2-5, §Assumptions]
- [ ] CHK020 Can all privacy and anti-cold-DM success criteria (`0` unauthorized profile activity exposures and `100%` non-friend/blocked message rejections) be objectively verified at the data-access boundary? [Measurability, Spec §SC-004, §SC-005]
